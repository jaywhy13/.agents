# Organized pull request story record

Start with the JSON artifact returned by `/pr-story`. The publisher validates it, resolves the signed-in Organized user from cached `quick auth` credentials, maintains the stable `pull_requests` parent, and appends an immutable `pull_request_versions` record whenever reader-facing content changes. Do not put the Organized user in `author`; that field always names the GitHub pull request author.

## Input fields

| Field | Type | Required | Meaning |
|---|---|---:|---|
| `title` | string | yes | Pull request title or an accurate manual title. Plain text on one line. |
| `summary` | string | yes | One plain-language sentence describing the outcome and why it matters. Plain text on one line. |
| `link` | string | yes | Exact canonical `https://github.com/owner/repository/pull/number` URL. No query, fragment, or trailing slash. |
| `repository` | string | yes | `owner/repository`, matching `link`. |
| `number` | positive integer | yes | Pull request number, matching `link`. |
| `author` | string | yes | GitHub username without a leading `@`. Never an Organized email. |
| `background` | Markdown string | yes | Concise prior system, vocabulary, motivating problem, constraints, scope, unchanged behaviour, and short Essential files and Essential symbols maps with one purpose per item. Must contain a heading and must not narrate the new implementation. |
| `intuition` | Markdown string | yes | Concise independent mental model, concrete example, or sustained analogy that defines only the conceptual roles needed to predict the change before code. Must contain a heading. |
| `code_story` | Markdown string | yes | Concise implementation narrative in conceptual order, with consequences, trade-offs, evidence locations, and unchanged behaviour. Must contain a heading; exact excerpts belong in `code_samples`. |
| `code_samples` | Markdown string | yes | Practical exact source examples showing how important components are constructed, called, tested, configured, or connected. Each sample names its file and symbol when available and states its purpose. Must contain a heading and at least one non-empty fenced `diff` excerpt copied from the pull request diff. Ends with the five-question comprehension check and visible answers. |
| `watch` | boolean | no | Watch intent. Defaults to `false` for a new record. When omitted during a refresh, the existing value is preserved. |
| `source_fetched_at` | ISO 8601 string | no | When GitHub metadata and the diff were fetched. |
| `source_diff_truncated` | boolean | no | Whether the source diff used to prepare the story was truncated. |

Conceptual diagrams belong inside `intuition` when they materially teach a flow, relationship, state transition, or before-and-after model; omit decorative diagrams. Mermaid diagrams use fenced `mermaid` blocks. Static images use Markdown image syntax with meaningful alt text and a safe `http://` or `https://` URL without embedded credentials. The publisher rejects unsupported top-level diagram or media fields.

Publish the verified record without presenting an approval preview or asking for confirmation. The `background`, `intuition`, `code_story`, and `code_samples` fields must complement one another rather than repeat the same explanation.

Raw HTML is not supported because Organized escapes it. Use a visible `## Answers` Markdown section rather than `<details>`.

## Managed fields

The publisher rejects these fields in input and sets them itself:

- `created_by`: authenticated Organized email from cached `quick auth` credentials;
- `ts`: creation time in epoch milliseconds, preserved on refresh;
- `created_at`: ISO creation time, preserved on refresh;
- `updated_at`: ISO time of the current publish or refresh;
- `watch_updated_at`: ISO time when watch intent last changed;
- `search_text`: lowercase searchable text built from the current story identity and teaching fields;
- `current_version_number`: version 1 for a new story or the latest meaningful content version; and
- `id`: generated by Quick when a record is created.

Each immutable version stores `pull_request_id`, `version_number`, the reader-facing input fields and source evidence, `created_by`, `created_from: agent_publish`, `ts`, and `created_at`. Re-publishing identical content or changing Watch alone does not create a version. Legacy parents and story versions may have empty `code_samples`; keep that absence honest rather than copying or inventing samples, and require Code Samples on their next save.

A refresh targets only a record with the same authenticated `created_by`, case-insensitive repository, and pull request number. Meaningful content changes append the next version and update the parent's current projection; identical content is a no-op unless Watch changed. A record belonging to another user is never updated. More than one matching record for the authenticated user is an error rather than choosing one arbitrarily.

## Example input

````json
{
  "title": "Make retries visible",
  "summary": "Operators can distinguish a retry from a first attempt without tracing separate identifiers.",
  "link": "https://github.com/shop/example/pull/42",
  "repository": "shop/example",
  "number": 42,
  "author": "octocat",
  "watch": true,
  "background": "## Why retries were confusing\n\nExplain the previous behaviour and its cost.\n\n### Essential files\n\n- `retry.js` — coordinates retry attempts.\n\n### Essential symbols\n\n- `createRetry` — creates another attempt for an operation.",
  "intuition": "## Think of one journey with several attempts\n\nDefine one concise mental model and only the roles it depends on.",
  "code_story": "## Carry attempt context\n\nExplain why retries retain both operation and attempt identity.",
  "code_samples": "## Create a retry\n\n**Location:** `retry.js` · `createRetry`\n\n```diff\n-old\n+new\n```\n\n## Check your understanding\n\n1. Why retain the identifier?\n\n## Answers\n\n1. It groups attempts under one operation.",
  "source_fetched_at": "2026-07-15T14:34:54.985Z",
  "source_diff_truncated": false
}
````

## Validate without writing

A dry run authenticates and reads existing records so it can accurately report `create` or `update`, but it does not mutate the database:

```bash
node ~/.agents/skills/organized-pr-story/scripts/publish-pr-story.mjs --dry-run /tmp/organized-pr-story.json
```

Both success and failure are printed as structured JSON. A successful real run returns the record identifier and its Organized detail URL.
