# Pull request story record

Prepare one JSON object for an Organized Pull Request Story. The publisher validates the story, resolves the signed-in Organized user from cached `quick auth` credentials, maintains the stable `pull_requests` parent, and appends an immutable `pull_request_versions` record whenever reader-facing content changed. Do not put the Organized user in `author`; that field always names the GitHub pull request author.

## Input fields

| Field | Type | Required | Meaning |
|---|---|---:|---|
| `title` | string | yes | Pull request title or an accurate manual title. Plain text on one line. |
| `summary` | string | yes | One plain-language sentence describing the outcome and why it matters. Plain text on one line. |
| `link` | string | yes | Exact canonical `https://github.com/owner/repository/pull/number` URL. No query, fragment, or trailing slash. |
| `repository` | string | yes | `owner/repository`, matching `link`. |
| `number` | positive integer | yes | Pull request number, matching `link`. |
| `author` | string | yes | GitHub username without a leading `@`. Never an Organized email. |
| `background` | Markdown string | yes | Prior system, vocabulary, motivating problem, constraints, why it matters, scope, and unchanged behaviour. Must contain a heading and must not walk through the new implementation. |
| `intuition` | Markdown string | yes | Independent mental model, concrete example, or sustained analogy that defines every conceptual role needed to predict the change before code. Must contain a heading. |
| `code_story` | Markdown string | yes | Literate implementation walkthrough in conceptual order, with evidence, consequences, trade-offs, and unchanged behaviour. Must contain a heading and at least one non-empty fenced `diff` excerpt. |
| `watch` | boolean | no | Watch intent. Defaults to `false` for a new record. When omitted during a refresh, the existing value is preserved. |
| `source_fetched_at` | ISO 8601 string | no | When GitHub metadata and the diff were fetched. |
| `source_diff_truncated` | boolean | no | Whether the source diff used to prepare the story was truncated. |

Conceptual diagrams belong inside `intuition` when they materially teach a flow, relationship, state transition, or before/after model; omit decorative diagrams. Mermaid diagrams use fenced `mermaid` blocks. Static images use Markdown image syntax with meaningful alt text and a safe `http://` or `https://` URL without embedded credentials. The publisher rejects unsupported top-level diagram or media fields.

Present the complete rendered `background`, `intuition`, and `code_story` in that order for approval before publishing. The fields must be complementary rather than repeat the same explanation.

Raw HTML is not supported because Organized escapes it. Use a visible `## Answers` Markdown section rather than `<details>`.

## Managed fields

The publisher rejects these fields in input and sets them itself:

- `created_by`: authenticated Organized email from cached `quick auth` credentials;
- `ts`: creation time in epoch milliseconds, preserved on refresh;
- `created_at`: ISO creation time, preserved on refresh;
- `updated_at`: ISO time of the current publish or refresh;
- `watch_updated_at`: ISO time when watch intent last changed;
- `search_text`: lowercase searchable text built from the current story identity, background, intuition, and code story;
- `current_version_number`: v1 for a new story or the latest meaningful content version; and
- `id`: generated by Quick when a record is created.

Each immutable version stores `pull_request_id`, `version_number`, the reader-facing input fields and source evidence, `created_by`, `created_from: agent_publish`, `ts`, and `created_at`. Re-publishing identical content or changing Watch alone does not create a version.

A refresh targets only a record with the same authenticated `created_by`, case-insensitive repository, and pull request number. Meaningful content changes append the next version and update the parent's current projection; identical content is a no-op unless Watch changed. A record belonging to another user is never updated. More than one matching record for the authenticated user is treated as an error rather than choosing one arbitrarily.

## Example input

```json
{
  "title": "Make retries visible",
  "summary": "Operators can distinguish a retry from a first attempt without tracing separate identifiers.",
  "link": "https://github.com/shop/example/pull/42",
  "repository": "shop/example",
  "number": 42,
  "author": "octocat",
  "watch": true,
  "background": "## 🌍 Why retries were confusing\n\nExplain the previous behaviour and its cost.",
  "intuition": "## 🧭 Think of one journey with several attempts\n\nDefine the mental model and the roles it depends on.",
  "code_story": "## 🪪 Carry attempt context\n\n```diff\n-old\n+new\n```\n\n## 🧠 Check your understanding\n\n1. Why retain the identifier?\n\n## ✅ Answers\n\n1. It groups attempts under one operation.",
  "source_fetched_at": "2026-07-15T14:34:54.985Z",
  "source_diff_truncated": false
}
```

## Validate without writing

A dry run authenticates and reads existing records so it can accurately report `create` or `update`, but it does not mutate the database:

```bash
node ~/.agents/skills/pr-story/scripts/publish-pr-story.mjs --dry-run /tmp/pr-story.json
```

Both success and failure are printed as structured JSON. A successful real run returns the record identifier and its Organized detail URL.
